# Failure modes → harness additions → measurements

A one-page map of the project ladder in [`learning-agent-harnesses-locally.md`](./learning-agent-harnesses-locally.md), read across instead of down: each rung exists to isolate *one* specific way small local models fail, add the smallest piece of harness scaffolding that compensates for it, and then measure whether the scaffolding actually earned its keep.

This is the practical form of the repo's core claim: every component in a harness encodes an assumption about what the model can't do on its own, and that assumption has to be tested rather than taken on faith — see "Why this matters" in the main doc.

| Project | Failure mode being isolated | Harness addition | What gets measured |
|---|---|---|---|
| [1. Bare-metal tool loop](./projects/01-bare-metal-loop/) | Model drops out of structured tool-calling and dumps a JSON-shaped guess into plain `content` instead | Retry-on-malformed-JSON, bounded by `MAX_JSON_RETRIES` | Pass rate over 10 trials with retry on vs. off, repeated on the 4B and the 9B |
| [2. Survive a restart](./projects/02-survive-restart/) | Zero memory across process restarts — a hard-killed run has nothing to resume from | Structured progress file (`state.py`) with atomic writes, read back on startup instead of an in-memory message list | Structured resume vs. naive replay-last-N-messages — the task length (turn count) where replay starts losing track while the structured file keeps working |
| [2.5 Run out of context on purpose](./projects/025-context-overflow/) | Finite context window (`num_ctx`) — a long task silently truncates history and the agent "forgets" what it was doing | A chosen compaction/reset strategy: summarize old turns, drop tool outputs but keep tool calls, or full reset from the progress file | Two strategies scored on the same task, then re-scored after halving `num_ctx` — does either strategy survive with less headroom? |
| [3. Permission-gated file agent](./projects/03-permission-gated-agent/) | An allowlist checked inside your own Python is still the agent policing itself — no real enforcement boundary | OS-level sandbox underneath the allowlist (container / Windows Sandbox / `bwrap`), plus a full audit log including refused actions | 5 escape techniques (`..` traversal, drive-relative paths, UNC paths, junctions, 8.3 short names) tried against the Python-only allowlist, then again with the sandbox underneath — the gap between those two numbers |
| [4. Generator–evaluator loop](./projects/04-generator-evaluator/) | Self-reported "done" isn't trustworthy — the model can claim success on a broken result | Separate generator/evaluator roles; a deterministic check (e.g. `pytest`) preferred over a second model call, with retry-with-feedback on failure | Generator self-reported success rate vs. evaluator-verified success rate across 20 tasks, and whether that gap narrows on the 9B |
| [5. Capstone — initializer/coding-agent](./projects/05-capstone/) | One-shotting the whole project in a single session, or declaring victory before the work is actually done | Initializer agent (writes `feature_list.json` + init script + first commit) and a coding agent that reads progress + `git log` first, then does one feature per fresh process | Ablate one component at a time (feature list / git-log read / commit-per-session) — which one, removed, breaks the run fastest |

Each row's measurement lives in that project's own `measurements/results.md` — this table is the index into those, not a replacement for them.
